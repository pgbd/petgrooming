# Spike S-2: concurrency

Result: **passes on MariaDB 11.4.14 locally** (five full runs, no failure). CI runs the same suite on a `mariadb:11.4` service; the VPS is not verified.
Defined in [TRD.md](../TRD.md) (rule 2 and Spikes) and [Plan.md](../Plan.md) (task S-2, Gate 1).

## What was tested

Each participant is a separate PHP process that boots the real application, connects, and waits for a shared "go" signal, so the two transactions genuinely overlap. The pattern under test is the TRD's: a transaction, `lockForUpdate()` on one concrete parent row (the resource), a half-open `[start, end)` overlap check, and a bounded retry count of three. Scratch tables live in a database whose name must end in `_spike`; the suite refuses to run elsewhere.

| Scenario | Expected | Result |
|---|---|---|
| Two parallel confirms, same resource and slot, eight rounds | exactly one confirmed, one conflict, one booking row | passed every round |
| Partly overlapping slots on one resource | one confirmed, one conflict | passed |
| Adjacent slots (one ends when the next starts) | both confirmed, because intervals are half-open | passed |
| Same time on two different resources | both confirmed, no blocking | passed |
| Negative control: same race without the row lock | both confirmed, a double booking | passed, so the race is real and the tests can fail |
| Deadlock: two transactions lock two resources in opposite order | one is rolled back and retried; both complete | passed, at least three attempts in total |

The negative control matters: it shows that without the lock the very same test code does double-book, so the "exactly one" result is caused by the lock and not by luck or timing.

## Environment

| Item | Value |
|---|---|
| Server | MariaDB 11.4.14 (Laragon, ADR-0006) |
| Isolation level | REPEATABLE-READ (the default) |
| Deadlock detection | on; lock wait timeout 50 |
| PHP | 8.4.27 |
| Retry mechanism | Laravel's transaction attempts (three) |

## What this proves

- A row lock on the parent resource serialises confirms for that resource, and an empty time range needs no lock of its own, which matches the TRD's rule.
- Half-open overlap behaves as specified at the boundaries.
- A deadlock is detected by the server and retried by the framework with no lost or duplicated booking.

## Gate 1

Gate 1 ("two confirmations cannot take the same slot") has its **first proof here** (spike in M0). It is still required to pass again against the real `ConfirmAppointment` action in M2 (task BK-2) and again in M6.

## Not verified

- **The VPS**: the same suite on the VPS MariaDB is not verified.
- This is spike code in `tests/Concurrency/Support`. The production `ConfirmAppointment` action does not exist yet and must pass these scenarios when it is built.
- Only two competing processes were used. Higher concurrency and sustained load are not tested; that belongs to the performance baseline (PERF-0) and M6.
- Locking behaviour on a resource-day row, hold expiry and rescheduling are not covered.
- `WITHOUT OVERLAPS` is a different spike (S-3).

## How to run

Create a database whose name ends in `_spike`, then:

```
DB_CONNECTION=mariadb DB_HOST=127.0.0.1 DB_PORT=3306 DB_DATABASE=<name>_spike DB_USERNAME=root DB_PASSWORD= vendor/bin/phpunit tests/Concurrency
```

Without those variables the suite is skipped, so the default `composer test` stays on SQLite.
